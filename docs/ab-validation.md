# A/B-валідація MCP (Task D)

**Промпт (однаковий для A і B):**
```
Which products in our catalog need reordering right now, and what is the
total value of the stock we are currently holding? Give me the SKUs and
the total as a number.
```

**Хост / модель:** Claude Code / Claude 3.5 Sonnet

**Сервер під тестом:** `mcp-server/` (tools: `search_inventory`, `low_stock` + resource `inventory://catalog`)

## Ground truth

Порахований локально, щоб було з чим звіряти:

```
SKU, що потребують дозамовлення: DK-4001, WC-8002, DS-6002, MS-2001, MN-3002, HS-5002, SS-1102, KB-1002, CB-7003
Загальна вартість запасів: $46,152.00
```

**Як розраховано:**
```bash
cd app && node -e "import('./dist/index.js').then(m=>{const c=m.loadCatalog();console.log('SKUs:', m.lowStock(c).map(p=>p.sku).join(', '));console.log('Value:', m.inventoryValue(c).toFixed(2));})"
```

Результат: 9 товарів нижче reorderLevel, загальна вартість всіх 24 товарів = $46,152.00

## Висновок

<НАПИШІТЬ 2–4 РЕЧЕННЯ>

**Ключові питання для висновку:**
1. Чи справді MCP змінив результат? (Краще: так, за рахунок X; гірше: ні, агент і без MCP прочитав JSON)
2. Якщо різниця меньша за очікувану — що це означає? (Коли власний MCP-сервер вартий своєї ціни, а коли достатньо простого доступу до файлів?)
3. Чесний нульовий результат тут цінніший за вигадану різницю — якщо агент і без сервера прочитав JSON правильно, це говорить про те, що модель вже досить хороша, і сервер — це just-nice-to-have, а не must-have.

**Приклад висновку:**
> MCP сервер значно прискорив відповідь: агент прямо викликав `low_stock` за одного крок вместо необхідності брати JSON, парсити та лічити вручну. Однак агент мав би прочитати JSON і сам (через filesystem) — сервер зменшив кількість операцій на ~60%, але не змінив принципову здатність модели вирішити завдання. Цінність MCP тут — в ергономіці, а не в запиту до можливості.
